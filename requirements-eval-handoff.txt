Findings: walt.id identity x openid4vp differential test (self-hosted, complete — round trip succeeded)

Setup: wallet-conformance-adapter (~/code/openid4vp/examples/wallet-conformance-adapter) run locally via `cargo run --example wallet-conformance-adapter -- --public-url http://localhost:9000` — actually listens on port 3000 regardless of --public-url (that flag only feeds the self-advertised `authorization_endpoint` in its own metadata document, a separate, hardcoded `--port` flag defaults to 3000 — CLAP arg definition confirmed in main.rs:21-22; the startup banner's "Public URL: http://localhost:9000" line is consequently misleading about where the server actually is, a minor first-time-user trap worth citing alongside the survey's other examples of this pattern (openid4vp's own unsigned-request trap, vc-js-cli's dead sample key)). Its one mock credential (~/code/openid4vp/examples/wallet-conformance-adapter/credentials.json) is a PID SD-JWT VC, vct=https://credentials.example.com/pid/1.0, claims {given_name, family_name, nationality, age_over_18} — confirmed NOT a static fake: matcher.rs:166-229 discards the fixture's placeholder MOCK_SD_JWT_SIG/MOCK_KB_SIG strings and re-signs live with a real hardcoded ES256 test-PKI issuer key (issuer.rs:45-58, self-signed "Conformance Test CA", iss=https://issuer.example.com) each time, computing fresh _sd digests over only the requested disclosures.

Six distinct, evidenced findings surfaced getting to a working round trip — each was a real result, not a dead end:

1. First attempt (unsigned default session from the portal's Verify->Advanced tab, template "[openid4vp-http][ietf sd-jwt vc] default dc+sd-jwt", DCQL edited to match the adapter's mock vct/claims): adapter rejected with "JWT headers were not valid base64url: Invalid byte 123, offset 0" (byte 123 = '{'). Root-caused by fetching the raw request_uri response directly: walt.id's verifier2 served Content-Type: application/json with a bare, unwrapped JSON object, not a JWT. Checked against primary spec text (WebFetch against openid.net's OID4VP 1.0 spec, section 5.10.1): "The Request URI response MUST be an HTTP response with the content type application/oauth-authz-req+jwt and the body being a signed, optionally encrypted, request object as defined in RFC9101" — no provision for plain JSON, even for unsigned requests (which per spec are still JWT-shaped, alg:none). This matches openid4vp's own cli-verifier README language ("Authorization requests are unsigned (alg: none) as required by spec") — both openid4vp examples independently assume JWT-wrapping is mandatory, consistent with the spec text. Net: walt.id verifier2's default/unsigned portal flow is spec-non-compliant on request_uri response format — a new, independent finding, distinct from the two previously-known walt.id wallet-side bugs (GH #692/#713) and from the already-fixed openid4vp alg_values bug.

2. Fixed by checking the portal's "signed_request" checkbox (Verify -> Advanced -> Request security options, previously collapsed) - new session correctly returned Content-Type: application/oauth-authz-req+jwt, a real ES256-signed JWT (verified by decoding: header carries x5c + kid, payload is a proper OID4VP authorization request object). Confirms walt.id can produce spec-correct request_uri responses; it just doesn't by default.

3. Client_id-scheme dropdown in the portal (showing "x509_hash (default & currently selected)") turned out to be cosmetic - the decoded JWT payload's client_id was still the bare "verifier2", no scheme prefix, and no client_id_scheme claim at all. Root-caused via the mounted service config, not the UI: waltid-identity/docker-compose/verifier-api2/config/verifier-service.conf:1-2 hardcodes `clientId: "verifier2"` with the properly-prefixed alternative (`#clientId: "x509_san_dns:verifier.example.com"`) commented out by default - the portal's dropdown has no wiring to this static, container-mounted file. Real UX/config-hygiene finding: a live-looking control that silently does nothing.

4. request_uri and response_uri both defaulted to host.docker.internal (verifier-service.conf:9, `urlPrefix: "http://${SERVICE_HOST}:${VERIFIER_API2_PORT}/..."`, SERVICE_HOST default in .env). Confirmed by direct test (not assumed): `curl` to host.docker.internal from the host shell failed with "Could not resolve host"; identical curl via localhost succeeded (200). host.docker.internal only resolves from inside Docker's network on this platform (Mac, Docker Desktop), not from a host-side process like the adapter (run via plain `cargo run`, not containerized) trying to reach in - backwards from what SERVICE_HOST's extra_hosts wiring (docker-compose.yaml host-gateway entries) actually supports, which is containers-reaching-host, not host-reaching-containers. Fixed by editing .env's SERVICE_HOST from host.docker.internal to localhost and `docker compose up -d --force-recreate verifier-api2`. Real, generalizable finding for anyone self-hosting this compose stack and testing from host-side tooling rather than another container.

5. With request_uri reachability fixed, a first pre-registered attempt (client_id still bare "verifier2", now correctly signed and JWT-wrapped) was rejected by the adapter: "unable to validate Authorization Request: 'pre-registered' client verification not implemented". Root-caused from source, not assumed: openid4vp's RequestVerifier trait (src/core/authorization_request/verification/mod.rs:55-65) ships a deliberate stub for the `preregistered` method (OID4VP 1.0 section 5.9.2: no ':' in client_id => pre-registered) that always bails - by design, since pre-registered trust requires out-of-band configuration a generic conformance-testing wallet can't provide generically. Checked whether switching to the config's commented-out `x509_san_dns:` alternative would help before suggesting it - it would NOT have: grep of the adapter's own `impl RequestVerifier for ConformanceWallet` (authorization.rs:559-583) shows only `x509_hash` and `redirect_uri` are actually overridden with real logic; x509_san_dns falls through to the same unimplemented-stub default. `redirect_uri` was also ruled out for this test specifically, since OID4VP 1.0 section 5.9.3 requires redirect_uri-scheme requests to be *unsigned*, conflicting with the signed-request setup already needed to fix finding #1. Worth flagging as a real, evidenced cross-implementation trust-posture difference (not directly re-tested here, but consistent with the earlier session's finding that wallet-api2's own default trust config, RequestContext.kt:28-32, has empty allow-lists across the board): openid4vp's reference wallet fails closed on an unverifiable pre-registered client_id, a conservative default; walt.id's own wallet-api2 trust config being empty suggests (not confirmed) it would accept the same pre-registered client_id permissively - two independent implementations facing identical spec-legitimate ambiguity ("what do you do with a pre-registered client_id absent a real registry") choosing opposite default postures.

6. Unblocked by switching verifier-service.conf's clientId to `x509_hash:<hash>` - computed directly from the leaf cert already present in the same config file's x5c field (SHA-256 of the DER bytes, base64url-no-pad encoded: OPpTDyXlg6WRu2-Qn4rpQcA9uVqSrNExCS8kCYUe09A), matching openid4vp's x509_hash::validate implementation (src/core/authorization_request/verification/x509_hash.rs) exactly. After restarting verifier-api2 and generating a fresh signed session: full round trip succeeded, confirmed by independent logs on both sides, not just one side's claim of success - openid4vp adapter log: DCQL matched_count=1, vp_token built token_entries=1, "Verifier response received status=200"; walt.id verifier-api2 container log, independently: "200 OK: GET - /verification-session/.../request" and "200 OK: POST - /verification-session/.../response". Adapter's HTTP response to the triggering /authorize call was `{}` - confirmed via source (authorization.rs:70-73, `SuccessResponse{redirect_uri: Option<String>}` with `skip_serializing_if`) to be the exact, correct serialization of a clean no-redirect success, not an ambiguous or silently-failed response.

Net assessment: walt.id's verifier2 (Kotlin, 0.23.0, new/default `identity` profile) and openid4vp's wallet-conformance-adapter (Rust, independently authored, built for OpenID Foundation conformance testing) successfully completed a real OID4VP 1.0 DCQL presentation exchange end to end once configured to a mutually-supported, spec-legitimate configuration (signed request, x509_hash client_id scheme). This is a genuine positive result for the differential-testing/neutral-compatibility-package idea (review sec 2.7) - two independent implementations, real crypto, real DCQL matching, no vcrd involvement, and every step (including every wrong turn along the way) was confirmed with primary evidence (spec text, source code, matched independent logs) rather than assumed. The wrong turns are themselves the more citable findings for Related Work: walt.id's default/unsigned demo flow doesn't meet OID4VP 1.0's request_uri content-type requirement; its portal UI has at least one control (client_id-scheme dropdown) that's disconnected from what's actually generated; its default self-hosted URLs (host.docker.internal) don't resolve for host-side test tooling; and its default clientId falls into a trust category (pre-registered) that a conservative reference wallet implementation deliberately refuses to accept. All are independent of, and in addition to, the two previously-known walt.id wallet-side bugs (GH #692/#713) from the earlier session.

Not yet done at the time of writing: the reverse direction (openid4vp's cli-verifier as verifier against walt.id's wallet-api2 as wallet, the original plan) - see next section, now done. Also not done: retesting the original hosted-demo bugs (disclosure-dropping, client_id-dropping) against this self-hosted new-stack instance directly - deprioritized per the earlier decision that the new stack is a rewrite, not a patch, so those specific old-stack bugs aren't expected to transfer either way.

Findings: reverse pairing - openid4vp's cli-verifier (verifier) x walt.id's wallet-api2 (wallet), self-hosted, complete (structural incompatibility found)

Setup, hands-on, real credential lifecycle end to end before the final blocking finding: created a wallet-api2 wallet (POST /wallet, empty body - CreateWalletRequest defaults auto-create key/credential/DID stores, confirmed from Wallet2RouteHandler.kt:218-229), generated a secp256r1 JWK key (POST .../keys/generate), set it default, created a did:jwk from it (POST .../dids/create). Issued a real credential via walt.id's own portal (Issue tab, OpenBadge/W3C VC JWT, pre-authorized) and redeemed it through wallet-api2's one-shot issuance endpoint (POST .../credentials/receive, ReceiveCredentialRequest{offerUrl}, confirmed from WalletIssuanceHandler.kt:100-124) - succeeded on the third attempt (see networking findings below), returning a real credentialId, not deferred.

Networking finding, a second confirming instance of the taxonomy gap first found in the verifier2 x wallet-conformance-adapter pairing (see above), this time in the opposite direction (container-to-container, not host-to-container): issuer-api2's issuance-offer machinery (issuer-service.conf:1, `baseUrl = "http://${SERVICE_HOST}:${ISSUER_API2_PORT}"` - the same SERVICE_HOST variable verifier-api2 uses) embeds itself as the offer's `credential_issuer` at two levels - the outer credential_offer_uri (fixable by hand-editing the URL we control) and, one level deeper, the fetched offer's own `credential_issuer` field used for .well-known metadata discovery (not fixable by hand-editing, since wallet-api2 fetches that document itself, server-to-server, invisible to the caller). With SERVICE_HOST left at the `localhost` value set earlier in this session (for the *other* pairing's host-based adapter), wallet-api2 - itself a container - correctly failed both times: `localhost` inside a container is that container's own loopback, not a sibling container, confirmed via full stack traces (CredentialOfferResolver.kt:59 for the first, shallower failure; IssuerMetadataResolver.kt:96 for the second, deeper one - both java.net.http ConnectException/ClosedChannelException). Reverted SERVICE_HOST to its original default (host.docker.internal) and recreated issuer-api2 only (docker compose up -d --force-recreate issuer-api2 - first attempt mistakenly recreated verifier-api2 instead, a real transcript error worth keeping as a reminder that these two services' configs are independently baked at container-start and don't share a live restart) - host.docker.internal correctly resolves from inside a container by round-tripping through the host's published ports, unlike localhost (container's own loopback) or a bare compose service name (would also have worked directly, not tried). Net, now three-way-confirmed network-audience finding for the taxonomy writeup: (a) real external wallet/browser on the host -> localhost works; (b) host-side standalone process/tool (not itself a container), e.g. wallet-conformance-adapter -> localhost works, host.docker.internal does not resolve from a host shell; (c) one container calling a sibling container, e.g. wallet-api2 -> issuer-api2 -> host.docker.internal works (round-trips via host's published ports), localhost does not (resolves to caller's own loopback). No single SERVICE_HOST value satisfies both (b) and (c) - a real, structural limitation of this compose stack's single-hostname config design, not incidental. Side effect worth noting: restarting issuer-api2 silently invalidated the in-flight offer session from before the restart - the portal's own browser tab kept SSE-polling the dead session ID every ~3s, producing a long but ultimately expected 404 "Issuance session not found" stack-trace stream (IssuanceSessionService.kt:16) until a fresh offer was created - confirms the offer/session store is not restart-durable, consistent with wallet2's own SQLite-backed-but-issuer2-not-necessarily-so storage split noted implicitly elsewhere in this survey.

Closing finding, the actual point of this pairing, confirmed structural (not a fixable default) via source on both sides: started openid4vp's cli-verifier (~/code/openid4vp/examples/cli-verifier) requesting jwt_vc format, `--public-url http://host.docker.internal:3000` (correct choice this time, since wallet-api2 as fetcher is itself a container - port-vs-public-url mismatch trap from the first pairing did not recur, since both default to the same port 3000 unless overridden). wallet-api2 correctly fetched the request_uri (confirmed via its own HTTP client debug log: 200 OK, `content-type: application/oauth-authz-req+jwt` - cli-verifier serves this correctly per spec, unlike walt.id's own unsigned-demo-mode verifier2 in the first pairing) but then immediately rejected it: `UnsignedAuthorizationRequestNotAllowedException: Unsigned AuthorizationRequest object (alg=none) is not allowed`. Root-caused precisely via source, not assumed: cli-verifier is hardcoded, by design, to the `redirect_uri` client_id_scheme, unsigned only - confirmed by reading its Args struct and inline comments (main.rs:58-90, "Per OID4VP v1.0 Section 5.9.3, requests using this scheme cannot be signed"), with no CLI flag to produce a signed request at all. wallet-api2's `/present` endpoint independently hardcodes the opposite extreme: `unsignedRequestObjectPolicy = UnsignedRequestObjectPolicy.REQUIRE_SIGNED` (WalletPresentationHandler.kt:1416), and the resolver's rejection gate (AuthorizationRequestResolver.kt:301-305) checks only `alg == "none"` with no client_id-scheme carve-out - so this isn't a demo-config default like the earlier verifier2 findings, it's a structural property of the shipped library: wallet-api2's public API cannot process a `redirect_uri`-scheme request under any configuration reachable through its own DTOs (PresentCredentialRequest has no such option). Net: two real, independently-maintained OID4VP 1.0 implementations are simply incompatible on this one spec-legitimate, no-PKI-needed configuration - neither side has a flag to route around it, and patching either is out of scope for a black-box eval per this survey's own no-integration rule. This is the mirror image of the first pairing's "openid4vp's reference wallet fails closed on pre-registered clients" finding: there, openid4vp's wallet was the conservative side; here, walt.id's wallet is the conservative side, on a different spec-legitimate low-trust configuration. Two independent, evidenced instances of the same underlying phenomenon (real implementations impose their own trust postures beyond bare spec minimums, and those postures don't always agree) - a strong, repeatable argument for the differential-testing/neutral-compatibility-package idea generally, not just a one-off finding.

Scope actually covered vs not: this pairing is now closed as "found a real, structural, well-evidenced incompatibility" rather than "completed a round trip" - a valid and useful outcome, not a failure of the test. Not attempted: modifying either tool to force compatibility (out of scope), or trying cli-verifier's other credential-format flags (mdl, ldp_vc, vcdm2_sd_jwt, ldp_or_mdl) - none would matter, since the blocking issue is client_id-scheme/signing, not credential format, and would reproduce identically regardless of which format-related flag was passed.

Findings: Credo-TS

Repo already cloned at ~/code/credo-ts (also listed as an additional working directory this session), node v22.15.0 via nvm, pnpm 10.22.0 pinned by the repo's packageManager field.

The official demo scripts are broken out of the box. Both `pnpm alice`/`pnpm faber` in demo/ and `pnpm issuer`/`pnpm holder`/`pnpm verifier` in demo-openid/ crash identically: "Error: TypeInfo not known for \"DidsApi\"" thrown from tsyringe's dependency-container.js, at Agent construction time. (demo-openid's `pnpm provider` script is not a counterexample — grep confirmed Provider.ts never constructs a Credo Agent at all; it's a bare oidc-provider OAuth server, so it was never going to hit this path regardless of runner.)

Root-caused, not assumed: ruled out two plausible-looking theories with real reproduction before accepting the real one, per the "get real evidence" convention. (1) Package-manager-version mismatch (system had pnpm 11.20.0, repo pins 10.22.0, an initial `pnpm install` had regenerated the lockfile) — ruled out: a clean install with the correctly pinned pnpm 10.22.0 reproduced the identical error. (2) Node version (credo-ts's own getting-started docs reportedly recommend v16/v18) — not fully ruled out by the user but very unlikely: a minimal two-class `tsyringe`/`vite-node` repro with zero credo-ts code failed identically on Node v22.15.0, and the mechanism is a compile-time transform gap, not runtime-version-dependent. Actual cause: both demo packages' scripts invoke plain `vite-node`, which transforms TS via esbuild, and esbuild does not implement TypeScript's `emitDecoratorMetadata` (no type checker, so it can't compute `design:paramtypes`) — which tsyringe's constructor injection requires. This is corroborated by the repo's own vitest.config.ts comment: "Specifically ESBuild does not support emitting decorator metadata, a feature we rely on heavily for class-transformer, class-validator and tsyringe." No `rolldown-vite` override (the maintainers' documented workaround) was present in this checkout's lockfile, though it may just be unneeded — see next point.

Confirmed it's not credo-ts itself, and not the user's environment: `pnpm test packages/core/tests/agents.test.ts` (which constructs `new Agent(...)` and drives the same DI graph) passes clean under vitest — 3/3, ~2.4s. So the framework's DI/decorator-metadata machinery works fine under the tooling the maintainers actually test with; only the demo packages' choice of runner is stale/broken.

Wrote a throwaway hands-on script, packages/core/tests/vcrd-eval.test.ts (heavily commented per user request, safe to `git clean` — not a credo-ts contribution), run via `pnpm exec vitest run packages/core/tests/vcrd-eval.test.ts --reporter=verbose` (plain `pnpm test <file>` passes too but suppresses the step console.logs). Full round trip, 1/1 pass: construct+initialize an Agent with `requireDidcomm: false` (no Askar native bindings, no wallet file, no network) → `agent.dids.create({ method: 'key', options: { createKey: {...} } })` for issuer and holder did:key DIDs (one call mints the key and derives the DID) → build a `W3cCredential` → `agent.w3cCredentials.signCredential({ format: ClaimFormat.JwtVc, ... })` → `agent.w3cCredentials.verifyCredential(...)` → `isValid: true` with a structured breakdown (`dataModel`, `signature`, `issuerIsSigner`, `credentialStatus` each independently flagged, not just one boolean — worth noting for vcrd's own verify-output shape). Ceremony total for a no-DIDComm in-memory issue/verify cycle: one Agent object, two DID-create calls, one sign, one verify — real but much lighter than the DIDComm-flavored demo scripts (which need Askar, a mediator-capable transport, and two coordinating agents before either side can do anything).

TS-vs-Rust angle (asked and answered explicitly this session, worth carrying into the Related Work write-up almost verbatim): this is a corroborating data point for vcrd's existing Rust choice, not new information that would move the needle. Reasoning, grounded in what was actually observed rather than generic language punditry: (1) TS's type erasure forces frameworks like this one to reconstruct type information at runtime via decorator metadata, and that reconstruction is tooling-dependent, not language-spec-guaranteed — the exact bug hit here (same source, silently different behavior under tsc vs esbuild, cryptic failure with no hint at the real cause) has no Rust analog, since rustc is the one compiler and the type system is resolved at compile time with no separate metadata-emission subsystem to go stale. (2) Credo-TS's own native dependencies (@hyperledger/anoncreds-nodejs, @openwallet-foundation/askar-nodejs, @hyperledger/indy-vdr-nodejs — all gated through pnpm's onlyBuiltDependencies allowlist as native N-API addons) are wrappers around Rust crates from the same OpenWallet/Hyperledger lineage — i.e. the TS ecosystem's own agent framework delegates the crypto-heavy core to Rust rather than implementing it in TS. (3) Distribution weight is qualitatively different for a thin-CLI use case: this one round trip needed a pinned package-manager version, a workspace-wide native-build allowlist, and picking the correct one of several coexisting TS transform pipelines (tsc / plain vite-node / vitest's transform) because they are not interchangeable for this codebase — versus a single Rust binary with no "which of three transpilers" axis at all. Caveat to preserve if this goes in the doc: none of this bears on Credo-TS's correctness once the right tooling is used (the library itself worked fine, isValid: true, correct verification breakdown) or on developer velocity/ecosystem breadth — it's specifically about a tooling-dependent bug class TS's reflection-based DI pattern has and Rust structurally doesn't.

Scope actually covered vs not, so the doc doesn't overclaim: only the core W3C JWT VC signCredential/verifyCredential path (via @credo-ts/core's Agent, DidsApi, W3cCredentialsApi) was exercised end-to-end. The openid4vc package (OpenID4VCI/VP), SD-JWT VC, and AnonCreds paths were read/traced (e.g. SdJwtVcService.test.ts, openid4vp-v1.e2e.test.ts) for API shape but not run. Credo-TS is not yet validated as a differential-testing oracle for anything — that would need a dedicated pass exercising verifyCredential against externally-sourced (non-Credo-generated) fixtures, which wasn't done this session.

A 2022 demo video (dated 2026-08-11 check: published 2022-11-14, made by Nick Reynolds — one of the three light-touch human contributors found in git log, confirming he's a real if lightly-active contributor) shows three issue/verify configurations, useful as a map of the plugin architecture's intended breadth: CLI-only with did:key and JWT (fully offline — did:key needs no resolution call); a Node.js app talking to a Heroku-hosted cloud agent with did:web and JSON-LD (requires real network reachability — did:web resolution is an outbound HTTPS GET, plus the hosted-agent dependency); and a React app via a MetaMask browser-extension wallet with did:ethr and EIP-712 (also requires real network reachability — did:ethr resolution needs an Ethereum RPC call to the on-chain registry, and EIP-712 is Ethereum's typed-data signing convention, not a W3C VC-DM proof suite — a web3-native extension of the framework's own uPort/ConsenSys lineage, not something vcrd would ever need to recognize). None of the three demoed configurations land in the "opens a local listener, no outbound call" middle network tier. The demo's specific artifacts have rotted (explore.veramo.dev, the React/MetaMask app, is dead) but its underlying plugin families (did-provider-key, did-provider-web, did-provider-ethr, credential-jwt, credential-ld, credential-eip712) are all still present in the current clone and were all touched during the v7.0.0 release cycle — the framework's shape is stable even where onboarding artifacts decay.

Installed `@veramo/cli` globally via npm (not Docker, unlike the SpruceID-stack and vc-js-cli sessions) — real distribution-weight numbers worth citing directly: 1,150 packages, ~1 minute install. Deprecation warnings included ones citing actual CVEs, not just staleness ("glob@7.2.3" and "tar@6.2.1" warnings explicitly reference "widely publicized security vulnerabilities, which have been fixed in the current version"). Native-binding install-script gate (npm's `allow-scripts`, the modern equivalent of the pnpm `onlyBuiltDependencies` allowlist that gated Credo-TS's native modules): `sqlite3` (the default local key/DID store backend) and `secp256k1` (backs the did:ethr/Ethereum-key path) were blocked by default, alongside a third package in the same gate that is not a functional dependency at all — `@scarf/scarf`, a package-analytics/telemetry tool whose postinstall script phones home install events by default. Recommendation carried forward: don't blanket-allow all three scripts; allow only `sqlite3,secp256k1` if the CLI needs them to function, leave `@scarf/scarf` blocked.

`veramo config create`'s generated `agent.yml` (schema version 3.0) is not a thin-CLI config — it scaffolds a full network-facing REST server by default: CORS, API-key auth, a WebDidDocRouter, a DIDComm MessagingRouter, an OpenAPI/Swagger UI, all bound to localhost:3332. That's real ceremony ("opens a local listener, no outbound call" tier) beyond anything Credo-TS or vc-js-cli required. The resolver config simultaneously reaches the "requires real network reachability" tier for several methods configured by default, not opt-in: `elem`/`io`/`ion`/`sov` route through the live Uniresolver dev instance (dev.uniresolver.io), and `ethr` routes through Infura mainnet+sepolia RPC using a project ID (`3586660d179141e3801c3895de1c2eba`) hardcoded in the CLI's own shipped template (`packages/cli/default/default.yml:187`) — confirmed via `git blame` to have been committed by Mircea Nistor on 2021-10-25, sitting in the public repo for nearly five years, not something specific to this local clone. Whether intentional shared demo key or an unrotated credential, don't rely on it for real testing; worth citing as precedent for vcrd's own example-config hygiene if it ever ships default configs (ties to the VC-example-library backlog item in requirements-review-handoff.txt). Also notable: `agent.yml`'s actual `defaultProvider` is `did:ethr:sepolia`, not did:key — contradicts a naive read of the 2022 demo's "CLI equals did:key" framing; did:key is still a registered provider but must be explicitly selected.

Two independent, stacked bugs found in the JSON-LD/Data-Integrity credential path specifically, both root-caused with real evidence rather than assumed, neither found reported anywhere by web search — likely the first documented instances of these exact manifestations. Bug 1: `veramo did providers` and `veramo did create` both crashed identically on Node v22.15.0 with a native (non-catchable) V8/Node assertion failure — `node::fs::InternalModuleStat`, "Assertion failed: (args.Length()) >= (2)", Abort trap: 6. Root-caused via `npm ls esm`: the chain is @veramo/cli → @veramo/credential-ld → @transmute/ed25519-signature-2018@0.7.0-unstable.82 (a prerelease-tagged dependency in a production framework, itself worth flagging) → @transmute/jsonld → jsonld → @digitalbazaar/http-client → esm@3.2.25, an abandoned module loader last published 2019-05-17 that patches Node's undocumented internal module-loading bindings directly. Confirmed via web search as a known, general Node regression class starting at v22.10.0 (algolia/shipjs#1006, shelljs#1180 hit the identical assertion from the same root cause; v22.9.0 confirmed still working) — not Veramo-specific, but this particular dependency chain wasn't found reported anywhere. Corrected after further testing, worth stating precisely rather than leaving the narrower first version stand: the durable fix is not "pin to the old patch v22.9.0" but "use current Node LTS" — user follow-up testing confirmed Node v24.19.0 (the actual current `lts/krypton`) also avoids the crash entirely, on an unmodified agent.yml. That the affected range is some-but-not-all of v22.x with v24.x LTS clear is itself informative: it means this unmaintained dependency's compatibility surface against Node's internals is unpredictable across versions, not a single clean cutover — the "current LTS" recommendation is safer than pinning any specific old version precisely because the boundaries of what's affected were never fully mapped.

Bug 2: independent of Bug 1, and now confirmed Node-version-independent rather than a tooling-fragility artifact — user follow-up reproduced the identical error on both Node v22.9.0 and Node v24.19.0 LTS: "Error creating @veramo/credential-ld['VeramoEd25519Signature2018']: Function.prototype.apply was called on undefined ... While creating object from pointer: /CredentialProviderLD." Since it survives a jump to current LTS unchanged, this is squarely a Veramo/Transmute integration bug, not a Node-compatibility one. Partially root-caused: confirmed the class is legitimately built and correctly re-exported from @veramo/credential-ld's compiled output (build/index.js exports it via `export * from './suites/Ed25519Signature2018.js'`), ruling out "missing/broken package" as the cause; narrowed to the CLI's own `$require`/JSON-pointer-based config composer failing to resolve the cross-package ESM named export at runtime, though the exact composer library was not identified (not bundled in @veramo/cli's own node_modules, and not conclusively traced further given diminishing returns). Corroborating detail from source: the class itself carries an `@alpha` doc comment ("This API is experimental and is very likely to change or disappear in future releases without notice") — an honest, self-declared status matching what was hit.

Net practical guidance, confirmed by direct comparison: on current Node LTS (v24.19.0), `@veramo/cli` installs and Bug 1 does not occur — "does not crash out of the box." But Bug 2 does still occur out of the box, on any Node version tested, so the JSON-LD path is broken regardless of Node choice and the agent.yml workaround (below) is still required to get anywhere. "More stable on current LTS, but doesn't exactly work out of the box" is the accurate summary.

Workaround applied and confirmed working: hand-edited `agent.yml` to remove the `CredentialProviderLD` block and its reference inside `credentialPlugin`'s args, leaving only `CredentialProviderJWT`. This fully unblocked the CLI. Full did:key/JWT round trip achieved and verified by hand-decoding, not just trusting the CLI's own success message: `veramo did create` (interactive prompts: provider=did:key, kms=local, alias=test001) produced `did:key:z6MkrZBMoA6Vm1GkgfEkLcG4s1c5s2QaR5jRDbRRBGycMoAH`; `veramo credential create` (interactive prompts: issuer/proofFormat=jwt/subject/type/claim) issued a JWT VC, hand-decoded to confirm a spec-correct VC-JWT encoding (header `alg: EdDSA, typ: JWT` matching the did:key's Ed25519 key type; payload correctly maps `iss`/`sub`/`nbf` from issuer/credentialSubject.id/issuanceDate per the JWT-VC claim-mapping rules, full credential nested under `vc`); `veramo credential verify -r <jwt>` returned "Credential was verified successfully."; a tamper test (flipping one byte of the JWT signature) correctly returned "Credential could not be verified." with no crash — a real, minimal correctness signal for the verify path, even without oracle-level validation.

Diagnosability finding, confirmed by both source reading and the tamper test's actual output, directly relevant to the diagnosability principle in requirements-review-handoff.txt: `packages/cli/src/credential.ts`'s verify command is strictly boolean (`result.verified === true` → success message, else a flat "Credential could not be verified.", no structured per-check breakdown of what failed — signature vs. expired vs. malformed vs. unresolvable issuer are all indistinguishable from the CLI's output). Sharp contrast with Credo-TS's structured `isValid`/`dataModel`/`signature`/`issuerIsSigner`/`credentialStatus` breakdown — two independent tools in this survey now under-deliver here, reinforcing diagnosability as a real, evidenced differentiator rather than a hypothetical one.

Ceremony total, for the comparison table: global npm install (1,150 packages) → generate config scaffold → hand-edit the generated scaffold to remove a plugin that is broken by default → multi-prompt interactive DID creation → multi-prompt interactive credential creation → separate verify invocation requiring the JWT to be hand-copied. Heaviest CLI friction of the three JS/TS tools evaluated (Credo-TS, vc-js-cli, Veramo). Architecture point distinct from any single bug: the `$require`-graph config model means one broken plugin anywhere in the default scaffold blocks every command, including ones with no logical connection to it — confirmed directly, since `did providers` (which touches no credential logic) crashed identically to `did create`. Not checked: whether the CLI supports non-interactive/flag-driven invocation to skip the prompts entirely — relevant if the "coding agents as primary ICP" framing (see requirements-review-handoff.txt) is pursued further, worth a follow-up if it matters later.

Ecosystem-breadth-as-scope-boundary, not a defect: alongside EIP-712 (above), `did:ens` — resolving an ENS (Ethereum Name Service) name as a DID — is specified and maintained by `veramolabs` itself (github.com/veramolabs/did-ens-spec), not DIF or W3C; it routes through the same Uniresolver dev-instance catch-all already used for elem/io/ion/sov, which in turn needs a live Ethereum RPC call to read the ENS registry — the heaviest-weight resolution path demonstrated across the whole session. Real ecosystem breadth, consistent with the ConsenSys/uPort lineage, but orthogonal to vcrd's W3C-VC scope.

TS-vs-Rust angle: a second, distinct corroboration of vcrd's Rust choice, not a repeat of the Credo-TS finding — worth keeping both since two independent bug classes is stronger evidence than one repeated. Credo-TS's bug was compile-time (esbuild's `emitDecoratorMetadata` gap, a TS type-erasure problem). This one is runtime VM-internal-API drift: an unmaintained package (esm@3.2.25, last released 2019) calling undocumented Node internals whose signature drifted at some unmapped point within the Node v22.x line, while current v24.x LTS happens to be clear. The follow-up finding sharpens rather than softens the point — the actual affected range was never characterized, so the honest description of the recourse is "run current LTS and hope," not "pin one known-good version." Rust's compiled, single-toolchain model has no equivalent "the VM's internal API drifted under me, and nobody mapped exactly where" failure axis for a shipped binary.

Scope actually covered vs not: only the did:key + W3C JWT VC create/verify path (via @veramo/cli's `did` and `credential` commands) was exercised end-to-end. The JSON-LD/Data-Integrity path was exercised only far enough to hit and root-cause its two bugs, not to a working round trip. OpenID4VCI/VP, SD-JWT VC, DIDComm messaging, and the did:ethr/did:web/did:ens/EIP-712 paths from the demo video were read/traced for API shape and architecture but not run. Veramo is not yet validated as a differential-testing oracle for anything — only a self-issued/self-verified round trip plus one tamper test were done; nothing was tested against externally-sourced VCs from another implementation.

Internal round-trip testing via the README's own documented curl flow (Initialize Transaction → Get authorization request → Send wallet response → Get wallet response → Get presentation events) surfaced real, evidenced README/reality drift, three separate instances on this one small endpoint surface: (1) `nonce` and one of `intended_use_id`/`registration_certificate` are actually required — hit `{"error":"MissingNonce"}` then `{"error":"MissingRegistrationCertificate"}` on requests built from the README's own documented (but not required-vs-optional-labeled) attribute list; the `develop` profile pre-configures one Intended Use (`verifier.intendedUses[0].id=1`) whose `registration-certificate` was usable directly. (2) The README's example Initialize Transaction response shows `"client_id": "x509_san_dns:localhost"`; the real `develop`-profile response is `"client_id": "x509_hash:i7jZiSqa4GXNh1LzBwD2lVtKIcIhpinRQRo8BHSVMx0"` — confirmed by decoding the actual signed request JWT's header/payload by hand (alg=ES512, typ=`oauth-authz-req+jwt` — spec-correct content type, contrast walt.id's earlier-found unsigned-demo-mode bug; a 2-cert x5c chain, leaf CN=verifier + intermediate, root omitted per convention, SAN=localhost/verifier, long-dated 2023–2123 dev cert). (3) The README's "Send wallet response" section documents a static URL, `http://localhost:8080/wallet/direct_post` — that route does not exist; the real, per-transaction `response_uri` (`/wallet/direct_post/{requestId}`) is only discoverable from the signed request JWT's own payload. Posting to the README's static URL produced a generic Spring 404 with a 9.2KB raw stack trace body (`spring.web.error.include-stacktrace=always`, `application.properties:5`) — a real diagnosability regression, not just a wrong-URL 404.

A second, independent config-vs-request mismatch found by inspecting the decoded request JWT closely: the `develop` profile's pre-configured WRPRC (registration certificate, `intendedUses[0]`) declares its `dc+sd-jwt` scope as `vct_values: ["urn:eudi:pid:1"]`, but the DCQL query actually sent (matched to openid4vp's `wallet-conformance-adapter` mock credential, for the later interop test) requested `vct_values: ["https://credentials.example.com/pid/1.0"]` — a completely different, out-of-scope vct. The verifier-endpoint embedded the registration certificate into the signed request with no validation that its own DCQL query falls within that certificate's declared scope. Checked whether the wallet side would catch this instead: grepped `wallet-conformance-adapter`'s full source for `verifier_info`/`registration_cert`/`WRPRC` — zero hits, it doesn't parse registration certificates at all — so this specific gap wouldn't surface as a wallet-side rejection either; a real, evidenced verifier-side validation gap, confirmed from source on both sides rather than assumed.

Diagnosability, a real three/four-way evidenced contrast on the Wallet API's input-handling surface, all from direct testing not speculation: (a) route-miss (the README's wrong static URL, above) → generic Spring 404, 9.2KB raw stack trace; (b) malformed `vp_token` JSON shape (a first attempt mistakenly reused the README's `mso_mdoc`-format placeholder value, `[{"id": "123456"}]`, for a `dc+sd-jwt` request) → uncaught `IllegalArgumentException` ("Given JSON doesn't comply with RFC7515. Misses payload", `SdJwtSerialization.kt:312`) → 500, another raw stack trace; (c) a syntactically-SD-JWT-shaped-but-cryptographically-bogus `vp_token` → a clean, structured `400 {"error":"InvalidVpToken","description":"[...]"}`with two named sub-errors (`UnableToDetermineVerificationMethod`, `ContainsInvalidJwt`), each with a spec-accurate description ("missing 'x5c' header claim, issuer is not an https url or did" correctly reflects SD-JWT VC's issuer-key-resolution rule) — arguably the single best error message in this whole multi-session survey; (d) a truncated/nonexistent transaction id → a clean, named `400 {"error":"PresentationNotFound",...}`. Net: exception handling is genuinely excellent once a request reaches real SD-JWT VC validation logic (`eudi-lib-jvm-sdjwt-kt` 0.20.1), but there's no upstream JSON-shape validation gate before dispatch, so wrong routes and malformed-shape payloads both leak raw Spring/Reactor internals.

A related, more subtle diagnosability finding, root-caused from source before concluding it was a bug: `GetWalletResponse`'s route handler (`VerifierApi.kt:200-201`) deliberately returns empty-bodied `404`/`400` for `NotFound`/`InvalidState` — but `GetWalletResponseLive.invoke()` (`GetWalletResponse.kt:130-134`) does compute a specific cause first (e.g. "Presentation should be in Submitted state but is in `Presentation$RequestObjectRetrieved`") and publishes it as a `PresentationEvent` before the empty response is returned. Confirmed live: `GET /ui/presentations/{transactionId}/events` returned exactly that cause string, plus a full timestamped, actor-attributed audit trail of the whole transaction (`Transaction initialized` → `Request object retrieved` → `Wallet failed to post response` → `Verifier failed to get wallet`, recorded twice for two identical polling attempts) — genuinely the strongest diagnosability feature in the whole multi-session survey, better than any single error response, it's just relocated to a separate endpoint rather than surfaced live, and nothing in the bare 400 hints that `/events` exists. Also worth noting: there are two distinct identifiers in play (`transaction_id`, used by VerifierApi endpoints like this one, vs. the request/`state` identifier embedded in the signed JWT, used by WalletApi endpoints) — correctly documented in the README's own prose, but easy to conflate in practice (done once this session).

Self-testability finding, a direct, evidenced answer to a question raised mid-session ("shouldn't an open-source package be able to test itself without external dependencies?"): `src/test/resources` ships matched `0X-dcql.json`/`0X-vpToken.json` fixture pairs (numbered 00–08) driving the JVM test suite (`WalletResponseDirectPostTest.kt`, `WalletResponseDirectPostJwtTest.kt`, etc.). At least one fixture, `08-invalidStatusList-vpToken.json`, contains a genuine, fully-formed, validly-signed SD-JWT VC + Key Binding JWT: real `_sd` digests, three real disclosed claims (`birthdate`, `given_name`, `family_name`), issuer `did:jwk:...` (a self-contained DID method needing no external resolution call), a real KB-JWT bound to `aud: "Sample Verifier Actor"`. So genuine self-test capability exists in this codebase — the maintainers built it — it's just scoped entirely to the internal JVM test harness (`WebTestClient`, in-process) and never surfaced as a documented, externally-usable script or CLI mode; nothing in the README hints at it. A sharper, more precise finding than a flat "can't self-test" complaint. Two caveats found on closer inspection, both worth keeping: (1) even this fixture isn't fully free of external dependency — its `status.status_list.uri` claim points to a live host, `https://issuer.eudiw.dev/token_status_list/...` (confirmed by decoding the SD-JWT's issuer-signed JWT payload directly), so with the base profile's default `verifier.validation.sdJwtVc.statusCheck.enabled=true` still in effect, exercising it for real would make a genuine outbound network call — the credential's signature/DID verification is offline, but full status-aware verification is not; (2) the JVM test that pairs these two fixtures explicitly expects failure (`fail("Expected to fail but didn't")` — `WalletResponseDirectPostJwtTest.kt:339`), and the DCQL query's credential `id` (`"sample_credential"`) doesn't match the `vp_token`'s top-level key (`"b7643d4c-..."`) — an inconsistency not resolved empirically before the session moved to the openid4vp interop attempt instead; worth investigating further if anyone picks this specific fixture pair up again.

One more README/API-surface gap, confirmed from source: the domain model's `authorization_request_uri` field (the ready-to-use `haip-vp://?client_id=...&request_uri=...` deep link) is present on `InitTransactionResponse.JwtSecuredAuthorizationRequestTO`, but the response DTO actually returned by the README's only documented Initialize Transaction endpoint (`POST /ui/presentations`, mapped to `VerifierApiVersion.V1`) is `JwtSecuredAuthorizationRequestV1TO` (`VerifierApi.kt:345-360`), which deliberately omits it. Only the undocumented sibling endpoint, `POST /ui/presentations/v2`, includes the field. Worked around by reconstructing the deep link by hand from `client_id`/`request_uri`/`request_uri_method`, same shape as what the `/events` log's richer "Transaction initialized" event already showed.

Findings: EUDI verifier-endpoint x openid4vp differential test (self-hosted, blocked — structural, root-caused algorithm-support gap)

Paired EUDI verifier-endpoint (as verifier) against openid4vp's `wallet-conformance-adapter` (as wallet) — the same "reverse pairing" shape as the earlier walt.id-session pairings (a real EUDI verifier speaking to an independent, conformance-suite-grade Rust wallet, not a bundled same-vendor counterpart). DCQL matched exactly to the adapter's own README sample config and its real bundled mock credential (`vct=https://credentials.example.com/pid/1.0`, claims `given_name`/`family_name`/`nationality`/`age_over_18`), `intended_use_id: "1"`. Checked feasibility from source before running: `submit_direct_post_jwt` in the adapter builds a real JWE per OID4VP §8.3, and its metadata advertises `ECDH-ES` plus both `direct_post`/`direct_post.jwt` response modes, matching EUDI's default `direct_post.jwt` — response encryption was not expected to be a blocker, and wasn't reached, since the failure occurred earlier in request parsing. (Also confirmed, per the WRPRC finding above, that the adapter doesn't parse `verifier_info`/registration certificates at all — it would not have caught that scope mismatch even if the flow had gotten further.)

Triggered by reconstructing the `authorization_request_uri` deep link by hand (see above) and swapping its `haip-vp://` scheme for `http://localhost:3000/authorize` — the adapter's real `authorization_get` handler, confirmed from its own source (`AuthorizationParams` struct, `server/handlers/authorization.rs`) before assuming the mechanism, same technique used successfully against walt.id's verifier2 in the earlier session. Blocked cleanly and structurally: `{"error":"invalid_request","error_description":"unable to decode Authorization Request Object JWT: unknown variant \`ES512\`, expected one of \`HS256\`, ..., \`ES256\`, \`ES384\`, \`ES256K\`, ..., \`AleoTestnet1Signature\`, \`None\`, \`none\`..."}`. Root-caused precisely, not left at the error text: EUDI's `develop` profile signs with ES512 (confirmed via the earlier hand-decoded JWT header, and independently via `docker-compose.yaml`'s own documented default, `VERIFIER_ACCESS_CERTIFICATE_SIGNING_ALGORITHM: "ES512"` — not a `develop`-profile-specific quirk, EUDI's own real-world default). openid4vp's JOSE dependency, `ssi-jwk` (SpruceID — same lineage as `didkit` from the earlier session), is pinned at exactly 0.4.0 in openid4vp's own `Cargo.lock`; its `Algorithm` enum (read directly from `algorithm.rs`, not inferred from the error text) defines `ES256`/`ES384`/`ES256K` plus several blockchain-specific curve variants (`ESKeccakK`, `ESBlake2b`, `AleoTestnet1Signature`) but has no `ES512` variant at all.

Checked for a config-only workaround before concluding this was structural: extracted the leaf cert's DER bytes from the earlier-decoded x5c and ran `openssl x509 -text` — confirmed a genuine 521-bit EC key (`id-ecPublicKey`). ES512 (ECDSA/P-521/SHA-512, RFC 7518) is the only standard JOSE algorithm that key supports; switching `VERIFIER_ACCESS_CERTIFICATE_SIGNING_ALGORITHM` to ES256 would need an entirely different P-256 key+cert, stepping back out of the self-contained `develop` profile into the external-keystore-mounting complexity this session deliberately avoided at the outset. No config-only fix exists.

Checked breadth before framing this as an `ssi-jwk`-specific oversight: WebFetch against docs.rs confirmed `jsonwebtoken` — the most widely-used Rust JWT crate — also stops at `ES384`, no `ES512` variant in its `Algorithm` enum. Two independent, widely-used Rust JOSE crates share this exact gap, not an isolated quirk in one library. Checked for a working counterexample rather than concluding the gap was unfixable in principle: docs.rs confirms `josekit` does support `ES512` (and `ES256K`) via its `EcdsaJwsAlgorithm` enum — full RFC 7518 ECDSA coverage is achievable in the Rust ecosystem today, just not via the two most popular/default crate choices. `josekit`'s own maturity/maintenance/dependency footprint was not independently evaluated this session — this is an existence proof, not a vetted recommendation.

Closed per this survey's own established rule (no patching either tool to force compatibility — same precedent as the earlier openid4vp cli-verifier x walt.id wallet-api2 pairing). User explicitly closed this as the session's final EUDI finding and stated the direct vcrd design takeaway: vcrd should (1) support as broad a set of JOSE signature algorithms as practical — citing `josekit` as evidence this is achievable, not an inherent Rust-ecosystem limitation, and (2) handle an unsupported-algorithm encounter gracefully — name the specific unsupported algorithm and, ideally, what is supported, distinguishing "well-formed request I don't support" from "malformed request," using `ssi-jwk`'s bare serde `unknown variant` message as a baseline-but-improvable example (specific and honest, but not framed for a caller trying to distinguish those two cases).

Session goal note, consistent with the earlier walt.id-session correction: like the earlier pairings, this is read for completeness/diagnosability/vcrd-design-input value, not as a pass/fail interop verdict — a clean, well-evidenced, structural incompatibility is a complete, valid outcome here, same as the earlier cli-verifier x wallet-api2 result.

Net: EUDI verifier-endpoint evaluation closed. Genuine internal round-trip tested end to end (including a full, deliberately-invalid-input error path and a look at the event-log audit trail); real diagnosability strengths and gaps characterized with direct evidence on both sides; a real, root-caused, structural interop finding with openid4vp that produced a concrete, actionable vcrd design requirement (broad algorithm coverage + graceful degradation), not just a descriptive data point. Remaining tool in this survey: anoncreds-rs (skim only, lowest priority) — see below.

Findings: anoncreds-rs (skim, lowest priority as scoped — not deep-tested)

Survey claims check out as written: Rust, Apache-2.0, reference implementation of the AnonCreds V1.0 spec, three-part issuer/prover/verifier service split — confirmed against `src/services/{issuer,prover,verifier}.rs` and the README, no corrections needed.

It's a pure library, not a CLI: no `[[bin]]` target anywhere in `Cargo.toml`, no `bin/` directory. Compiles to `staticlib`/`rlib`/`cdylib` plus an `ffi` feature; the only wrapper actually in this repo is `wrappers/python` (thin ctypes-style binding over the FFI) — the Node.js and React Native wrappers the README lists live in a separate external repo. So today there is no existing thin, vcrd-shaped CLI sitting on top of anoncreds-rs.

Asked directly (user prompt): is there a vcrd-style CLI backed by anoncreds-rs? Checked the closest candidate the user has hands-on history with, ACA-Py (~/code/acapy), specifically to answer this rather than assume. It's a full DIDComm agent framework — controller/admin-API pattern, docker-based Alice/Faber demo scripts under `demo/` — not a thin single-binary inspector; same shape complaint this survey already made about Credo-TS relative to vcrd's goals. Net: no existing tool fills the "thin vcrd-style CLI over anoncreds-rs" niche. Real, citable gap, but not this session's job to fill — worth a one-line "possible future direction, post-§9" note rather than an action item now. Not an exhaustive crates.io/GitHub search — a skim-level check only, consistent with this item's scoped priority.

Notable and directly relevant to vcrd's data model: anoncreds-rs has a `w3c` submodule (`src/services/w3c`, `src/data_types/w3c`) that converts legacy AnonCreds credentials/presentations to and from real W3C VC Data Model v1.1/v2.0 JSON, confirmed via a real round-trip test in the 3695-line `tests/anoncreds_demos.rs` demo suite (`anoncreds_demo_works_for_issue_legacy_credential_convert_into_w3c_and_present_w3c_presentation`, and its reverse), not just claimed in docs. Checked the proof layer specifically before treating this as a generic-oracle candidate: the W3C envelope carries the proof as a `DataIntegrityProof` tagged `AnonCredsDataIntegrityProof` (`src/data_types/w3c/credential.rs`, `proof.rs`) with AnonCreds-specific `CredentialSignature`/`CredentialPresentation`/`Presentation` proof-value variants — a real W3C VC wrapper, but not a signature a generic (non-AnonCreds-aware) verifier could check. So it's not usable as a differential-testing oracle for vcrd's *current* verification path, but it is a well-formed, spec-shaped fixture source for whenever §9 AnonCreds support lands.

Input to the `ProofSuite` trait design question (REQUIREMENTS.md:254-259, which already flags that AnonCreds/BBS+ needs room for partial/selective-disclosure proofs from the start): the demo suite's `PresentAttributeForm` enum (`RevealedAttribute` / `UnrevealedAttribute` / `Predicate`) is a concrete, working example of that shape — confirms the existing design note, doesn't change it.

Consistency check against last year's close review of anoncreds-clsignatures-rs (the underlying CL-signature math crate, reviewed separately by the user, not re-touched this session): anoncreds-rs depends on it as an ordinary crate (`anoncreds-clsignatures = "0.3.2"` in `Cargo.toml`), a clean, unsurprising dependency boundary — no contradictions surfaced between the two reviews.

Net: anoncreds-rs evaluation closed at the scoped skim depth — survey claims confirmed, no CLI exists (a real gap, flagged not filled), a concrete W3C-envelope fixture source identified for future §9 work, and the `ProofSuite` partial-disclosure design note corroborated. This closes the ecosystem survey — all six tools (Credo-TS, vc-js-cli, Veramo, walt.id identity, EUDI verifier-endpoint, anoncreds-rs) now evaluated.

Context: vcrd is a Rust CLI/library for reading, validating, and verifying W3C verifiable credentials. Repo at ~/code/vcrd. Design doc is REQUIREMENTS.md; it was reviewed producing REQUIREMENTS-REVIEW.md (prompt that generated it: requirements-review-prompt.txt). The review's recommendations need to be folded into the doc across several sequenced sessions — this handoff covers everything decided or learned so far, so this session can pick up the actual editing.

Positions settled during discussion (ready to write into the doc)
No direct dependency on ssi or any other ecosystem library — interop demonstrated, not coupled. This sharpens §14.1 beyond the review's "evaluate ssi, price in SpruceID risk" framing: the decision is to never depend on ssi/openid4vp/isomdl/etc. in vcrd-core's Cargo.toml, full stop, and instead demonstrate interoperability via a differential-testing harness (ties to review §2.7 and the "neutral compatibility-testing package" idea). Rationale given: vcrd should stay standalone, universal, and unopinionated in a way a company-backed library optimizing for its own product line (SpruceID's mDL/gov-ID business) structurally can't guarantee to stay.
Read-only/no-network by default is retained, but needs a three-tier taxonomy, not a binary. (a) fully offline — today's inspect/validate/offline verify; (b) opens a local listener, no outbound call — e.g. standing up a local server for a wallet-interaction protocol; (c) requires real network reachability — a tunnel, port-forward, or proximity channel making that listener reachable. (b) is a materially different risk shape (inbound exposure) than (c) or than did:web-style outbound resolution, and may warrant its own explicit opt-in flag distinct from --allow-network. This came directly out of hands-on protocol testing this session (see evidence below) — in every test, vcrd/openid4vp-style tooling never dialed out itself; the user made the network-reachability decision explicitly and separately (running ngrok), which is arguably more honest to the no-network-by-default spirit than DID resolution already is.
Diagnosability needs to be a named, extended principle, not just implicit in "graduated success." §5 already has "results represent graduated success, not pass/fail" for the parse→validate→verify pipeline. The extension: when something fails, especially in a future live-protocol-exchange capability, vcrd should structurally pin down which tier failed, whose side it's on, and why — not require the user to hand-decode base64url tokens and cross-reference spec text the way this session had to. This is the best-evidenced single point from this session (see appendix) and connects to review item 2.4 ("what was not checked" should be first-class) as a related but distinct idea worth cross-referencing when both get written up. A concrete, settled sub-requirement fell out of the EUDI verifier-endpoint session (separate parallel session, appendix below): algorithm support needs to be (a) as broad as practical across standard JOSE signature algorithms, not just the common subset, and (b) fail gracefully and specifically when it isn't — naming the unsupported algorithm and, ideally, what is supported, rather than an opaque parse failure. This is directly evidenced, not aspirational: EUDI's real default signing algorithm (ES512/P-521) turned out to be unsupported by two independent, widely-used Rust JOSE crates (ssi-jwk, jsonwebtoken — both stop at ES384), blocking an otherwise-clean interop round trip outright; a third crate, josekit, does support the full ECDSA family, confirming this is a crate-selection question vcrd can get right, not an inherent Rust-ecosystem limitation. Not yet scoped into a section (candidate: §5 alongside diagnosability, plus a concrete crate-selection note wherever vcrd's JOSE dependency gets chosen — josekit's own maturity wasn't vetted, just confirmed to have the right algorithm coverage on paper).
vcrd-net replacement is live, not settled. User is open to replacing the tcpdump-style vcrd-net (which the review recommends dropping for ethical/legal reasons — §14.6) with a protocol-level live-verifier feature: request a real presentation from a mobile wallet (motivating example: a CA mDL) via QR code + local server (or a public tunnel, informed by the user's prior ACA-py tunneling experience), using something like the openid4vp crate's approach. This session's hands-on testing (below) validated the protocol-level approach is technically workable for verifiers and surfaced a hard scope boundary: government-grade wallet trust is gated by ecosystem accreditation (AAMVA Digital Trust Service / IACA trust lists for mDL specifically), not just a valid TLS cert — a real, external limit worth documenting explicitly rather than treating as a solvable engineering problem. The decision to actually remove vcrd-net is explicitly framed as low-stakes/reversible either way.

Appendix: evidence from this session's hands-on testing
didkit: archived (July 2025), needed small cargo-build fixes to compile — matches review's framing but confirms it's not unusably stale.
ssi: still actively released (v0.16.0, Apr 2026), modular sub-crates.
isomdl: builds and tests cleanly, ships its own fixtures, no official ISO vectors needed.
openid4vp: found and fixed a real spec-compliance bug (alg_values → alg_values_supported, confirmed against spec text and the crate's own self-contradicting doc comment; all 116 tests still pass after the fix). Confirmed the crate's unsigned (redirect_uri, alg: none) example requests are correctly rejected by any wallet enforcing verifier authentication — not a bug, working as designed, but a trap for a first-time user assuming "it fetched the request" means "it's working."
walt.id wallet: two separate bugs found independent of anything on the vcrd/openid4vp side, on the hosted demo — disclosures dropped regardless of selection (GH #692), and client_id dropped during walt.id's own internal by-reference→by-value request reconstruction (confirmed via direct response-body inspection, not guessing). CORRECTION (added in the later self-hosted walt.id session, see appendix entry below): "still-open" was wrong for the first bug — checked against GitHub's actual API/timeline, #692's disclosure-dropping symptom was fixed via a follow-up issue (#713), closed 2024-08-28, roughly two years before this session. The hosted demo tested here was evidently running code that predated that fix, or hit a re-manifestation of the same symptom class; either way, don't write "still-open" into REQUIREMENTS.md without a version/date caveat. The second bug (client_id dropped) has no public GitHub issue at all, so its status remains genuinely unverified — not retested against the self-hosted new stack (deliberately deprioritized, since that stack is a rewrite of the affected code, not a patch — see appendix).
CA DMV Wallet: unreachable for this kind of testing without ecosystem trust accreditation — confirmed as a hard, non-engineering boundary.

Credo-TS (separate parallel session, full detail in requirements-eval-handoff.txt): the official demo/ and demo-openid/ scripts are broken out of the box (tsyringe "TypeInfo not known" at Agent construction), root-caused — not assumed — to esbuild not implementing emitDecoratorMetadata, which the framework's tsyringe-based DI requires; the repo's own vitest.config.ts comment corroborates this independently. Confirmed it's neither the user's environment nor a real credo-ts bug: an existing core test (agents.test.ts) constructs an Agent and passes clean under vitest, so only the demo packages' choice of runner (plain vite-node) is stale. Wrote a throwaway, heavily-commented packages/core/tests/vcrd-eval.test.ts exercising the real hands-on comparison point — construct an Agent, create issuer+holder did:key DIDs, sign a W3C JWT VC, verify it — 1/1 pass, isValid: true with a structured per-check breakdown. Ceremony for a no-DIDComm in-memory issue/verify cycle: one Agent object, two DID-create calls, sign, verify — lighter than the DIDComm demo flows but still real Agent/DI overhead versus vcrd's zero-object CLI model. TS-vs-Rust language question was asked directly and answered with evidence (not priors): this reads as corroboration of vcrd's existing Rust choice — TS's type erasure forces reflection-based DI whose correctness depends on which build tool ran it (a bug class Rust structurally can't have, since rustc is the only compiler and the type system is resolved at compile time), and Credo-TS's own native dependencies (askar-nodejs, indy-vdr-nodejs, anoncreds-nodejs) are themselves N-API wrappers around Rust crates — the TS ecosystem's own agent framework delegates crypto to Rust. Caveat to keep if this goes in the doc: this says nothing about Credo-TS's correctness (fine once the right tooling is used) or developer velocity/ecosystem breadth — it's specifically about a tooling-dependent bug class. Not yet validated as a differential-testing oracle for anything; only the core W3C JWT VC path was run end-to-end, not OpenID4VCI/VP, SD-JWT VC, or AnonCreds.

vc-js-cli (Digital Bazaar, separate parallel session, full detail in requirements-eval-handoff.txt) — evaluated by code-reading only, not run, so don't overclaim this as hands-on: attempting vc-demo's Docker alias hit a linux/amd64-vs-arm64 platform-mismatch warning on the user's arm64 Mac; rather than debug Docker further, switched to reading the source directly (small enough to read in full). Git history is the sharpest finding: 14 commits total, and the last functional commit (Use vc-js@0.2.0) is dated 2019-09-15; the only 2024 activity (3 commits, same day) was an eslint bump, making index.js executable, and a README wording note — zero logic changes. So this is not just "low activity" (the eval doc's original framing) but functionally frozen for 5+ years against a pre-1.0 vc-js dependency, 2019-generation LD-proof suites (Ed25519Signature2018, not the newer eddsa-rdfc-2022/Data Integrity suites), and stale transitive deps (axios ^0.18.1, commander ^2.20.0) — real evidence against treating it as a current-spec differential-testing oracle (§2.7), though it could still work as a narrow smoke-check limited to basic Ed25519Signature2018 JSON-LD credentials specifically. keygen hard-requires a GitHub personal access token by design (lib/key.js throws immediately if none given) and publishes the key+controller documents as two private GitHub gists, referencing them by raw URL as issuer/verificationMethod — effectively a 2019, pre-did:web hack for "publish a key at a stable resolvable URL," worth citing as informal historical precedent for what did:web later formalized. The bundled "offline" sample-key.json doesn't actually support a self-contained round trip: its id/controller are the W3C spec's placeholder example.edu URLs, and verify has no local fallback for resolving verificationMethod — it always does a live HTTP GET — so the shipped sample is a trap for a first-time user assuming it works standalone (same shape as the openid4vp unsigned-request trap noted elsewhere in this appendix). One real positive precedent for vcrd's own document-loader thinking: unlike verificationMethod resolution, common JSON-LD @context documents are bundled as a static local map (contexts/index.js) rather than fetched live — even a thin, largely-abandoned tool made the offline-by-default call for that piece. On distribution: the Dockerfile is plain node:12-alpine with only pure-JS deps (axios, commander, jsonld-signatures, etc. — nothing native), so the amd64-only Docker Hub image is a packaging/CI gap, not an architectural constraint — a second, independent data point (after Credo-TS's native-binding story) for the "distribution weight" theme: a single cross-compiled Rust binary doesn't have this failure mode by construction. Shape takeaway, given this tool was prioritized specifically as "closest existing thing in shape to vcrd": index.js + lib/api.js together are well under 150 lines total — confirms the thin-CLI-over-a-VC-library shape is genuinely easy to build. What's actually hard, and what vcrd needs to demonstrate value on, is the maintenance/spec-currency/offline-guarantees/no-vendor-lock substance this repo doesn't have — not the CLI plumbing itself.

Veramo (separate parallel session, full detail in requirements-eval-handoff.txt) — evaluated hands-on: cloned, installed @veramo/cli globally, worked through two independently-confirmed bugs to a full did:key/JWT issue-verify round trip. Org lineage: uPort (ConsenSys, 2015) → relaunched as Veramo under ConsenSys Mesh (~2020) → donated to DIF; governance is DIF-in-name but effectively single-maintainer in practice — of 43 trailing-year commits, 34 are from one person (Mircea Nistor), against 83 open GitHub issues and only 1 non-bot open PR; his LinkedIn lists no employer since MetaMask ended Aug 2025, consistent with (not proof of) currently-unpaid maintenance. A Nov 2022 demo video maps the plugin architecture's intended breadth (CLI+did:key+JWT fully offline; Node+Heroku+did:web+JSON-LD and React+MetaMask+did:ethr+EIP-712 both requiring real network reachability) — EIP-712 (Ethereum typed-data signing) and a separate did:ens method (ENS names as DIDs, spec'd by veramolabs itself, not DIF/W3C) both demonstrate real web3-native ecosystem breadth orthogonal to vcrd's W3C-VC scope. Installing the CLI pulled 1,150 packages including deprecation warnings citing actual CVEs and a native-binding install-script gate that swept in `@scarf/scarf`, an install-telemetry package, alongside the two legitimate native deps (sqlite3, secp256k1) — don't blanket-allow. The generated `agent.yml` scaffold wires a full REST server by default (not a thin CLI) and hardcodes a five-year-old public Infura project ID (committed 2021-10-25, still shipped) for its default did:ethr resolution. Two independent, stacked, previously-unreported bugs were root-caused in the JSON-LD/Data-Integrity credential path specifically: a Node-version-sensitive regression in a dead (2019) transitive dependency (esm@3.2.25, via credential-ld → an 0.7.0-unstable Transmute package → jsonld → digitalbazaar/http-client) that crashes on some Node v22.x builds but was confirmed clear on current v24.19.0 LTS — a known general Node bug class, but this exact dependency chain undocumented elsewhere, and the affected v22.x range was never fully mapped, so "run current LTS" is the honest recommendation rather than pinning one known-good old version; and, independent of and confirmed to persist across both Node versions tested, a separate ESM-export-resolution failure in the CLI's own config composer, narrowed but not fully traced. Net: Veramo does not crash out of the box on current Node LTS, but does not fully work out of the box either — the second bug still requires trimming the JSON-LD plugin out of agent.yml regardless of Node version. That trim fully unblocked the did:key/JWT path — confirming both bugs are specific to the JSON-LD subsystem, not systemic: the resulting VC-JWT was hand-decoded and spec-correct, and verify correctly rejected a hand-tampered signature. Sharpest single finding: verify's CLI output is strictly boolean (confirmed from source and the tamper test) with no structured breakdown of what failed, a direct, evidenced contrast with Credo-TS's structured per-check output — now feeding the "coding agents as primary ICP" discussion above. Not yet validated as a differential-testing oracle — only self-issued/self-verified, nothing against externally-sourced VCs.

walt.id identity (separate parallel session, full detail in requirements-eval-handoff.txt) — evaluated hands-on, self-hosted via waltid-identity/docker-compose (not waltid-enterprise-quickstart, which turned out to require paid Enterprise Stack access — a correction to the original eval plan, and itself a citable data point: walt.id splits into a free/open community stack and a gated paid one, echoing the existing SpruceID/ssi "company-backed library" framing in §14.1). The repo bundles two stacks (`identity-old`, draft/PEX-based, matching the hosted demo tested earlier; `identity`, the new default, DCQL-based OpenID4VP 1.0) — only the new default was tested this session. Two paired differential tests against openid4vp, in both directions: (1) walt.id's real verifier2 against openid4vp's wallet-conformance-adapter (an independent, conformance-suite-grade Rust wallet) succeeded end to end — confirmed by matching, independent logs on both sides (DCQL match, vp_token built, `200 OK` on both request and response legs) — a genuine, working, positive validation of the differential-testing/neutral-compatibility-package idea (review §2.7), not just a hoped-for approach. Getting there surfaced real, spec-text-confirmed findings along the way: walt.id's default/unsigned demo mode serves a bare, unwrapped `application/json` request object where OID4VP 1.0 §5.10.1 requires `application/oauth-authz-req+jwt`; the portal UI's client-id-scheme selector is cosmetic (the real value comes from a static, container-mounted config file, `x509_san_dns` left commented out by default); and self-hosting surfaces a genuine three-audience network-hostname problem (external browser/wallet vs. host-side tooling vs. container-to-container) that no single `SERVICE_HOST` value satisfies at once — direct, concrete evidence for the network-taxonomy work (review item, §5/§7). (2) The reverse pairing (openid4vp's cli-verifier as verifier, walt.id's wallet-api2 as wallet) failed cleanly and instructively: cli-verifier is hardcoded to the unsigned `redirect_uri` client-id scheme (spec-legitimate, no-PKI-needed, per OID4VP 1.0 §5.9.3), and wallet-api2's public API hardcodes `REQUIRE_SIGNED` with no override exposed anywhere — confirmed this is an API-surface gap, not a library gap, since walt.id's own test suite exercises `ALLOW_UNSIGNED` at the library level. Initially mischaracterized as a "structural incompatibility" between two disagreeing implementations; corrected on user recall that the *old* walt.id stack behaved the same way, and that CA DMV Wallet (from the earlier openid4vp session, see line 30/32 above) also refuses unauthenticated redirect_uri requests — the accurate framing is two independent real wallets landing on the same sane security policy, not a compatibility bug. Net assessment, framed around completeness/usability/diagnosability rather than a pass/fail interop table (this survey's actual goal, not a compatibility matrix): walt.id is the most complete and usable tool evaluated this session — full OID4VCI+OID4VP coverage across JWT/SD-JWT/mdoc, a genuinely good manual-testing portal UI, specific/named exceptions (`UnsignedAuthorizationRequestNotAllowedException`, contrast Veramo's flat boolean), and a granular preview/resolve-request/match-credentials API shape that's a real external precedent for vcrd's own graduated-success principle — offset by self-hosting-specific networking friction and a couple of UI/config defaults that silently overpromise (the cosmetic client-id dropdown, the silently-non-compliant unsigned demo mode). Also relevant to the "coding agents as primary ICP" discussion: walt.id's REST API is fully scriptable, JSON throughout, no interactive prompts anywhere in this session's testing — a positive counter-example to Veramo's interactive-only CLI friction.

EUDI verifier-endpoint (separate parallel session, full detail in requirements-eval-handoff.txt) — the EU wallet reference-implementation program's standalone Verifier/RP service (Kotlin/Spring Boot, Apache-2.0), evaluated hands-on, self-hosted. First real decision: the shipped docker-compose.yaml hardcodes a placeholder IP (10.240.174.10, traced to the README's own documentation examples, not a deployment leftover) and builds a full TLS/haproxy stack for cross-device QR testing — deliberately skipped in favor of `./gradlew bootRun` with Spring's `develop` profile, which turned out to be a genuinely self-contained local-dev config (classpath-bundled keystore, `x509_hash` client-id scheme, permissive issuer trust by default, in-memory persistence) needing no external files or IP at all — a positive precedent worth citing for how a project can make local self-testing easy without Docker. Internal round-trip testing (README's own documented curl flow) surfaced three separate, evidenced instances of README/reality drift on one small endpoint surface (undocumented-required `nonce`/`intended_use_id` fields; a stale example client_id scheme; a documented static wallet-response URL that isn't a real route, the real one being per-transaction and only discoverable from the signed request JWT itself) — each cost real debugging time, a concrete, citable argument for vcrd's own example/doc accuracy discipline. Diagnosability findings were a genuine mixed bag with sharp contrasts on both ends, all direct evidence: a route-miss and a malformed-payload-shape both leaked raw 9-11KB Spring/Reactor stack traces to the client, while a syntactically-plausible-but-invalid credential produced the single best error message in this whole multi-session survey (a named `InvalidVpToken` error with structured, spec-accurate sub-error codes) — meaning excellent exception handling exists in this codebase once a request reaches real validation logic, but there's no upstream shape-validation gate catching malformed input before then. A related, subtler finding: the wallet-response-status endpoint deliberately strips its own internally-computed failure cause from the live HTTP response, but the full cause (plus a complete timestamped, actor-attributed audit trail) is captured in a separate presentation-events endpoint — arguably the strongest diagnosability feature in the whole survey, just non-obviously located. Directly answering a question raised mid-session (shouldn't an OSS verifier be able to test itself without external dependencies?): it actually can — the JVM test suite ships genuine, validly-signed, offline-verifiable SD-JWT VC fixtures (did:jwk issuer, no resolution call needed) — but that capability is scoped entirely to the internal test harness and never surfaced as a documented, externally-usable self-test mode; one such fixture also turned out to depend on a live status-list host despite otherwise being offline-capable, showing even the maintainers' own best self-test tooling didn't fully achieve dependency-free self-testing either. The closing, most consequential finding came from a differential-testing pairing against openid4vp's wallet-conformance-adapter (same reverse-pairing shape as the walt.id pairings above): DCQL/trust configuration was worked out cleanly (matching the adapter's real mock credential, correct x509_hash client-id, correct JWE response-mode support confirmed on both sides from source first), but the round trip was blocked structurally — EUDI's real default signing algorithm, ES512 (P-521, confirmed via the shipped cert's actual key size, not assumed), is unsupported by openid4vp's JOSE dependency (ssi-jwk 0.4.0), whose Algorithm enum stops at ES384. Checked for a config-only fix (none exists — the key material itself is P-521-only) and checked breadth before blaming one crate: jsonwebtoken, the most popular Rust JWT crate, has the identical gap, while a third crate, josekit, does support the full ECDSA family — turning this from "an unfixable interop hole" into a concrete, evidenced vcrd design requirement (see the diagnosability item above): support the full standard JOSE algorithm set, and fail specifically and by-name when an algorithm isn't supported, rather than an opaque parse error. Net, consistent with this survey's actual goal (completeness/usability/diagnosability, not a pass/fail interop matrix): EUDI verifier-endpoint is solid, spec-careful software with real strengths (excellent validation-layer error messages, a genuinely useful event-log audit trail, permissive-by-default local self-hosting) and real, evidenced gaps (doc/reality drift, an unguarded upstream input-validation layer, an unsurfaced self-test capability) — and produced this session's most concrete, actionable input for vcrd's own JOSE-layer design.

Context: vcrd is a Rust CLI/library for reading, validating, and verifying W3C verifiable credentials. Repo at ~/code/vcrd. Design doc is REQUIREMENTS.md; it was reviewed producing REQUIREMENTS-REVIEW.md (prompt that generated it: requirements-review-prompt.txt). The review's recommendations need to be folded into the doc across several sequenced sessions — this handoff covers everything decided or learned so far, so this session can pick up the actual editing.

Positions settled during discussion (ready to write into the doc)
No direct dependency on ssi or any other ecosystem library — interop demonstrated, not coupled. This sharpens §14.1 beyond the review's "evaluate ssi, price in SpruceID risk" framing: the decision is to never depend on ssi/openid4vp/isomdl/etc. in vcrd-core's Cargo.toml, full stop, and instead demonstrate interoperability via a differential-testing harness (ties to review §2.7 and the "neutral compatibility-testing package" idea). Rationale given: vcrd should stay standalone, universal, and unopinionated in a way a company-backed library optimizing for its own product line (SpruceID's mDL/gov-ID business) structurally can't guarantee to stay.
Read-only/no-network by default is retained, but needs a three-tier taxonomy, not a binary. (a) fully offline — today's inspect/validate/offline verify; (b) opens a local listener, no outbound call — e.g. standing up a local server for a wallet-interaction protocol; (c) requires real network reachability — a tunnel, port-forward, or proximity channel making that listener reachable. (b) is a materially different risk shape (inbound exposure) than (c) or than did:web-style outbound resolution, and may warrant its own explicit opt-in flag distinct from --allow-network. This came directly out of hands-on protocol testing this session (see evidence below) — in every test, vcrd/openid4vp-style tooling never dialed out itself; the user made the network-reachability decision explicitly and separately (running ngrok), which is arguably more honest to the no-network-by-default spirit than DID resolution already is.
Diagnosability needs to be a named, extended principle, not just implicit in "graduated success." §5 already has "results represent graduated success, not pass/fail" for the parse→validate→verify pipeline. The extension: when something fails, especially in a future live-protocol-exchange capability, vcrd should structurally pin down which tier failed, whose side it's on, and why — not require the user to hand-decode base64url tokens and cross-reference spec text the way this session had to. This is the best-evidenced single point from this session (see appendix) and connects to review item 2.4 ("what was not checked" should be first-class) as a related but distinct idea worth cross-referencing when both get written up.
vcrd-net replacement is live, not settled. User is open to replacing the tcpdump-style vcrd-net (which the review recommends dropping for ethical/legal reasons — §14.6) with a protocol-level live-verifier feature: request a real presentation from a mobile wallet (motivating example: a CA mDL) via QR code + local server (or a public tunnel, informed by the user's prior ACA-py tunneling experience), using something like the openid4vp crate's approach. This session's hands-on testing (below) validated the protocol-level approach is technically workable for verifiers and surfaced a hard scope boundary: government-grade wallet trust is gated by ecosystem accreditation (AAMVA Digital Trust Service / IACA trust lists for mDL specifically), not just a valid TLS cert — a real, external limit worth documenting explicitly rather than treating as a solvable engineering problem. The decision to actually remove vcrd-net is explicitly framed as low-stakes/reversible either way.

Appendix: evidence from this session's hands-on testing
didkit: archived (July 2025), needed small cargo-build fixes to compile — matches review's framing but confirms it's not unusably stale.
ssi: still actively released (v0.16.0, Apr 2026), modular sub-crates.
isomdl: builds and tests cleanly, ships its own fixtures, no official ISO vectors needed.
openid4vp: found and fixed a real spec-compliance bug (alg_values → alg_values_supported, confirmed against spec text and the crate's own self-contradicting doc comment; all 116 tests still pass after the fix). Confirmed the crate's unsigned (redirect_uri, alg: none) example requests are correctly rejected by any wallet enforcing verifier authentication — not a bug, working as designed, but a trap for a first-time user assuming "it fetched the request" means "it's working."
walt.id wallet: two separate, live, still-open bugs found independent of anything on the vcrd/openid4vp side — disclosures dropped regardless of selection (GH #692), and client_id dropped during walt.id's own internal by-reference→by-value request reconstruction (confirmed via direct response-body inspection, not guessing).
CA DMV Wallet: unreachable for this kind of testing without ecosystem trust accreditation — confirmed as a hard, non-engineering boundary.

Credo-TS (separate parallel session, full detail in requirements-eval-handoff.txt): the official demo/ and demo-openid/ scripts are broken out of the box (tsyringe "TypeInfo not known" at Agent construction), root-caused — not assumed — to esbuild not implementing emitDecoratorMetadata, which the framework's tsyringe-based DI requires; the repo's own vitest.config.ts comment corroborates this independently. Confirmed it's neither the user's environment nor a real credo-ts bug: an existing core test (agents.test.ts) constructs an Agent and passes clean under vitest, so only the demo packages' choice of runner (plain vite-node) is stale. Wrote a throwaway, heavily-commented packages/core/tests/vcrd-eval.test.ts exercising the real hands-on comparison point — construct an Agent, create issuer+holder did:key DIDs, sign a W3C JWT VC, verify it — 1/1 pass, isValid: true with a structured per-check breakdown. Ceremony for a no-DIDComm in-memory issue/verify cycle: one Agent object, two DID-create calls, sign, verify — lighter than the DIDComm demo flows but still real Agent/DI overhead versus vcrd's zero-object CLI model. TS-vs-Rust language question was asked directly and answered with evidence (not priors): this reads as corroboration of vcrd's existing Rust choice — TS's type erasure forces reflection-based DI whose correctness depends on which build tool ran it (a bug class Rust structurally can't have, since rustc is the only compiler and the type system is resolved at compile time), and Credo-TS's own native dependencies (askar-nodejs, indy-vdr-nodejs, anoncreds-nodejs) are themselves N-API wrappers around Rust crates — the TS ecosystem's own agent framework delegates crypto to Rust. Caveat to keep if this goes in the doc: this says nothing about Credo-TS's correctness (fine once the right tooling is used) or developer velocity/ecosystem breadth — it's specifically about a tooling-dependent bug class. Not yet validated as a differential-testing oracle for anything; only the core W3C JWT VC path was run end-to-end, not OpenID4VCI/VP, SD-JWT VC, or AnonCreds.
